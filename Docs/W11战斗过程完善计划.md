## 1. 计划目标

本计划的第一目标不是增加更多敌人、Boss 或章节，而是把当前“可以扣血并完成结算”的架构纵切，完善为一场具有明确攻防节奏、信息可读、结果可解释、单人可闭环、联机可同步的 2D 动作战斗。

第一轮交付完成后，玩家应当能够：

1. 仅通过画面与声音区分瘴灵、残剑魂、石甲妖的攻击方式；
2. 在伤害发生前看见明确预警，并使用移动或闪避作出反应；
3. 理解每次伤害的来源、命中位置、实际数值、护障吸收和会心结果；
4. 随时看清气血、真元、护障、攻击/术法/闪避冷却和当前战斗目标；
5. 在胜利或死亡后进入唯一、稳定、不会重复结算的收口流程；
6. 在相同技能定义下切换任意角色时，规则与技能特效资源保持共享，不产生“角色 × 技能”副本。

第一轮同时必须建立可扩展的战斗实例边界：每场战斗拥有唯一 `EncounterInstanceId`，所有请求、延迟攻击、投射物、预警和结果都能归属到该实例；战斗终局只能由一个服务器权威入口裁决。该边界属于首轮规则地基，不推迟到波次或 Boss 阶段。

第一轮目标战斗使用固定 Seed `424242`，以一场约 90～150 秒的单人试炼作为初始节奏标尺。该时长是试玩调参目标，不是写死的流程计时器。

## 2. 当前基线

截至 2026-08-29，以下内容已经存在：

- `AW11Character` 已支持正交俯视相机、四向平面移动、四向基础攻击、门派初始术法和服务器校验闪避；
- 闪避已有 `0.75` 秒冷却、最多 `260 uu` 胶囊 Sweep 位移和 `0.20` 秒伤害免疫；
- `UW11CombatComponent` 已在服务器校验攻击间隔、真元、范围、范围半径、会心和命中；
- `UW11AttributeComponent` 已统一气血、真元、护障、护体减伤、治疗、回元和伤害免疫；
- 已有六个门派初始术法、三类敌人、三段遭遇、修为奖励和仙坊流程；
- 十名角色已有左右向 `Idle / Move / Cast / Hit` Flipbook，门派术法与通用命中火花已作为角色无关资源导入；
- `AW11GameMode`、`AW11GameState`、`AW11PlayerState` 和 `AW11RunDirector` 已形成服务器权威状态机；
- 固定 Seed `424242` 的 NullRHI 冒烟与 `WorldWalker.W11` 三项架构测试已通过。

以下仍是当前主要缺口：

- 基础攻击的伤害、间隔、距离和半径仍由 `UW11CombatComponent` 的成员字段固定，不是 `BasicAttackAbility`；
- 三类敌人的行为本质相同，都是追踪最近玩家并在近距离按固定间隔直接扣血；
- 敌人没有数据驱动的前摇、攻击生效段、后摇、预警形状、弹道或硬直；
- 玩家攻击和术法没有统一的伤害结果/表现事件，命中火花还不能可靠定位到真实受击目标；
- `AW11HUD` 仍为空壳，没有正式中文战斗 UMG；
- 没有完整的单人死亡、局终、残余攻击清理和防重复结算流程；
- 当前阶段仍是 `Combat → Cultivation → ImmortalMarket → Combat`，仙坊尚未迁移为章节地图节点；
- 本段是计划启动前基线；截至 2026-08-30，四主动槽、Burn/Slow 状态运行时、五类遭遇、机制组合精英、Boss 数据契约、章节节点交接接口和五章候选路线均已实现。五张独立地图已被章节资产引用并通过加载契约；章节间实际视觉切换与节点密度仍需真人冻结和验收。

## 3. 实施边界

### 3.1 必须遵守

- 伤害、治疗、护障、状态、位移合法性、资源消耗和胜负只能由服务器决定；
- 客户端只提交技能、目标方向或闪避请求，不提交最终伤害和命中目标；
- 角色只拥有外观、通用动作和先天属性；技能规则与技能 VFX 不按角色复制；
- 普通攻击必须迁移为共享 `BasicAttackAbility`，且不占四主动技能槽；
- 闪避保持独立基础动作，不占普通攻击或主动技能槽；
- 气血、真元、护障、装备、存活状态和战斗终局等持续事实使用复制状态；冷却、前摇、生效与后摇优先复制服务器时间戳和状态快照，不逐帧复制剩余秒数；短暂命中火花、受击闪白和声音使用轻量表现事件；
- 纯表现资源缺失时允许安全降级，但不得改变命中、伤害或胜负；
- 正式 HUD 以 `3840×2160`、16:9 为制作与终验基准，同时回归 2560×1440、1920×1080 和 1280×720；
- 新增或改变系统职责、战斗流程、输入、依赖或验证方式时，同步更新 `Docs/项目活文档.md`。

### 3.2 本计划不提前决定

- `Q / W / E / R` 逻辑槽在键鼠上的最终默认物理按键；
- 普攻最终采用方向键、鼠标瞄准、自动索敌还是可切换方案；
- 合作倒地、救援、全队失败与章节复归规则；
- 房主掉线、重连或主机迁移方案；
- 每章战斗、事件、休整和仙坊节点的最终数量。

这些问题在上位冻结表中仍未决定。实现时只建立可重绑定的逻辑动作和可扩展接口，不把临时输入写成最终产品规则。

## 4. 目标战斗流程

第一轮单场战斗采用以下流程：

```text
进入战斗节点
  ↓
服务器锁定遭遇定义与 Seed
  ↓
清理上一场残余对象和临时状态
  ↓
显示试炼名称、目标与短暂开场提示
  ↓
按遭遇规则生成首批敌人
  ↓
敌人循环：选目标 → 接近/站位 → 前摇预警 → 生效 → 后摇
玩家循环：移动/瞄准 → 普攻/主动术法 → 闪避 → 观察反馈
  ↓
每次命中生成统一战斗结果并驱动表现
  ↓
持续检查玩家存活、遭遇目标和残余威胁
  ├── 玩家死亡：冻结结算 → 清理威胁 → 本局失败入口
  └── 目标完成：清理威胁 → 胜利演出 → 发放一次奖励
  ↓
进入安全阶段
```

当前原型仍可在胜利后进入修炼和仙坊，但第一轮必须把“仙坊必定出现”视为兼容流程，不把它固化进新的战斗完成接口。后续章节路线接入后，由地图节点决定下一阶段。

## 5. 核心规则改造

### 5.1 普通攻击技能化

扩展 `UW11AbilityDefinition` 或其通用效果结构，使普通攻击与主动技能共用以下最小规则字段：

- 稳定技能 ID、玩家可见名称和逻辑槽类型；
- 目标模式：自身、方向、目标点、自动目标；
- 命中形状：点、圆、胶囊/线、扇形、投射物；
- 基础伤害、威力系数、攻击间隔或冷却；
- 真元消耗；普通攻击第一版为零消耗；
- 基础距离、半径、角度、投射物速度和最大目标数；
- 是否允许重复命中、贯穿或只命中一次；
- 角色动作类型和 `UW11SkillVisualDefinition` 软引用；
- 可供秘籍修改的行为标签。

规则字段还必须明确以下缩放和确定性契约：

- 普攻间隔由 `AttackSpeedScale` 缩放，主动技能冷却由 `AbilityHaste` 缩放；除非定义显式声明，不允许同一冷却同时接受两种缩放；
- 会心按“每次施法一次”还是“每个目标一次”由定义声明，首轮基础攻击沿用每次施法一次；
- 多目标查询在应用 `最大目标数` 前按稳定规则排序，首轮使用“距离 → 稳定 SpawnId”，不得依赖物理查询返回顺序；
- 目标模式、命中形状、命中传递方式和效果负载分层表达，避免把“圆形选点”和“投射物如何命中”固化成同一个枚举分支。

玩家运行时装备结构目标为：

```text
BasicAttackAbility       1 个，永不为空
ActiveAbilitySlots       4 个逻辑槽，可为空或更换
Dodge                    角色固有，不占技能槽
```

第一轮只要求完成一个基础攻击定义和当前门派初始术法的兼容迁移；不要求立即制作完整四槽内容池。

### 5.2 统一战斗请求与结果

建议增加以下纯数据结构，名称可在实现时按 Unreal 反射约定调整：

```text
FW11AbilityRequest
├── EncounterInstanceId
├── 逻辑槽（服务器据此解析已装备 Ability，不接受客户端指定最终规则）
├── 输入方向或目标点
└── 客户端请求序号

FW11DamageSpec
├── 仅由服务器构造的来源、技能、基础伤害与威力系数
├── 伤害标签、是否允许会心
├── 状态效果负载
└── 命中方向与位置

FW11AbilityExecutionResult
├── EncounterInstanceId、客户端请求序号、权威执行序号
├── 是否接受、失败原因、服务器冷却结束时间
├── 来源、AbilityId / 逻辑槽
└── 0～N 个 FW11EffectResult

FW11EffectResult
├── 结果类型：Damage / Heal / Barrier / Mana / Status
├── 来源、目标、AbilityId、稳定目标 ID
├── 伤害时：原始伤害、护体减免、护障吸收、实际气血伤害
├── 其他效果时：请求量、实际变化量、状态与持续/叠层结果
├── 是否会心、是否免疫、是否击败
└── 命中位置、方向

FW11CombatCue
├── EncounterInstanceId、SourceStableId、Cue 类型与权威执行/效果序号
├── 来源、目标、位置、方向
└── 表现标签
```

客户端请求不得携带可信的施法者、基础伤害、资源消耗或最终 Ability 定义。服务器必须从拥有该 RPC 的组件、Pawn、PlayerState 与逻辑槽推导施法者和装备技能，并拒绝以下输入：

- 非有限数值（NaN / Inf）、零方向、未归一化方向或越界目标点；
- 旧 `EncounterInstanceId`、重复/倒退请求序号或非当前战斗阶段请求；
- 死亡、不可战斗、施法锁定、冷却中、资源不足或未装备槽；
- 超出定义距离、阵营、目标数量、重复命中与穿透规则的目标。

失败原因只发送给请求玩家，并携带客户端请求序号，供 HUD 对应显示“真元不足”“冷却中”“无合法目标”等提示。`FW11DamageSpec` 是服务器内部对象，不作为客户端请求或可信复制输入。

目标调用链为：

```text
输入适配层
  → UW11CombatComponent 提交/校验技能请求
  → 目标查询与效果计算
  → UW11AttributeComponent 应用最终结果
  → 产生 FW11AbilityExecutionResult / FW11EffectResult
  → 角色、敌人、HUD、声音和 VFX 消费 FW11CombatCue
```

`UW11AttributeComponent` 继续拥有气血、真元、护障与免疫事实，但应返回足够详细的伤害拆分结果，避免表现层通过生命差值猜测护障或减伤。

权威执行序号至少在单个施法者内单调递增，和 `EncounterInstanceId` 一起组成去重键；必须定义整数回绕后的比较方式。持续复制状态负责晚加入和丢包恢复，Cue 只负责允许丢失的瞬时表现，不用 Cue 维持冷却、前摇或终局事实。

### 5.3 敌人战斗状态机

`AW11EnemyController` 第一版使用显式状态，不再在 Tick 中“距离足够近便直接扣血”。最小状态为：

```text
AcquireTarget
Approach / Reposition
Windup
Active
Recovery
Stagger（预留）
Defeated
```

状态要求：

- `Windup` 开始时锁定本次攻击需要的方向或目标规则；
- 预警形状由服务器确定，客户端只绘制；
- 到达 `Active` 时服务器重新做必要的合法性校验并结算命中；
- 取消、死亡或战斗结束必须让预警失效，不得延迟造成幽灵伤害；
- `Recovery` 期间不能立即再次攻击，但允许根据定义决定能否转向或移动；
- 选择目标时排除已经死亡或处于无效阶段的玩家；
- AI 决策 Tick 与表现帧率解耦，不能依赖 Flipbook 播放完成决定权威命中时点。

攻击参数进入 `UW11EnemyDefinition` 或独立敌方技能定义，不按敌人名字在 Controller 中写分支。

`AW11EnemyController` 只在服务器执行决策。客户端可见且影响反应窗口的攻击事实必须复制到 `AW11Enemy`、专用战斗组件或独立预警 Actor，最小快照为：

```text
FW11ReplicatedAttackState
├── EncounterInstanceId / AttackInstanceId
├── 攻击定义 ID、当前状态
├── 锁定目标的稳定 ID，或锁定方向/落点
├── 预警形状与权威几何参数
└── WindupStart / Active / RecoveryEnd 的服务器时间
```

客户端按服务器时间显示剩余前摇；状态快照必须支持丢包后的下一次复制恢复和中途加入恢复。网络延迟不得悄然吞掉大部分反应窗口：试玩时同时记录服务器设定前摇与客户端实际可见提前量，低于门槛时通过更早复制、最小前摇或表现补偿解决，而不是延后服务器命中事实。

### 5.4 三种敌人的首轮行为

| 敌人 | 战斗职责 | 首轮行为 | 主要反制 |
|---|---|---|---|
| 瘴灵 | 远程走位压力 | 与玩家保持中距离，显示方向预警后发射缓慢瘴气弹；弹体命中或寿命结束后销毁 | 横向移动、绕行、闪避穿过危险窗口 |
| 残剑魂 | 闪避时机测试 | 短暂锁定方向，显示狭长直线预警，随后沿该方向冲刺斩击并进入明显后摇 | 离开直线、晚闪避、利用后摇输出 |
| 石甲妖 | 空间封锁与重击 | 缓慢追近，显示圆形范围后重砸；高护体但攻击结束暴露较长硬直 | 保持距离、诱导落点、后摇集中攻击 |

首轮建议调参区间：

- 普通攻击前摇：约 `0.45～0.90` 秒；
- 残剑魂冲刺线与石甲妖重砸圈必须在前摇开始时可见；
- 远程弹体速度应允许正常移动规避，不制作无预警命中扫描；
- 同屏预警使用稳定色义和形状，不用只靠粒子亮度区分；
- 不增加无预警接触伤害；角色与敌人胶囊接触本身不应持续扣血。

具体数值必须通过试玩调整，不在文档中冻结为最终平衡。

## 6. 战斗表现

### 6.1 命中反馈层级

每次有效命中至少按以下顺序提供反馈：

1. 攻击动作或技能释放；
2. 命中目标处播放共享命中火花；
3. 受击目标播放 `Hit` 动作或短暂局部受击反应；
4. 目标出现短暂闪白/着色；
5. 显示实际气血伤害、护障吸收或免疫提示；
6. 播放与攻击类别匹配的命中声音；
7. 会心使用独立但克制的数字样式和声音层；
8. 击败时播放死亡反馈并延迟清除表现，不再固定 `0.2` 秒立即消失。

命中火花必须使用对应 `FW11EffectResult` 的目标与命中位置，不能继续挂在施法者身上猜测位置。

### 6.2 打击停顿与镜头

- 单机和联机共用的战斗规则不得依赖全局 `TimeDilation`；
- 第一版打击停顿只冻结相关 Flipbook、局部材质或表现计时，不暂停服务器状态机；
- 普通命中、会心、重击和 Boss 破防使用分级反馈，避免每次攻击都同样震动；
- 屏幕震动、闪光和数字必须提供强度上限，保证多人同屏和 4K 画面可读；
- 表现事件丢失不得影响伤害事实，重复收到同一结果序号不得重复播放关键反馈。

### 6.3 角色与技能动画

第一轮优先顺序为：

1. 命中火花正确定位；
2. 受击、死亡和攻击预警可读；
3. 共享战斗声音；
4. 补充真正的上/下方向角色帧；
5. 制作专属闪避帧并替换当前移动动作回退。

上下帧和闪避帧属于表现里程碑，但不得阻塞服务器规则、敌人状态机和命中反馈测试。

## 8. 胜利、死亡与清理

### 8.0 权威终局与战斗实例边界

`AW11GameMode` 或等价服务器权威对象统一持有：

```text
EncounterInstanceId
CombatOutcome = Pending / Victory / Defeat
OutcomeReason
OutcomeSequence
```

所有胜利条件、玩家死亡和主动终止都只能调用同一个 `TryFinalizeCombat` 入口。第一次从 `Pending` 成功迁移到终局的调用负责设置结算锁、推进 OutcomeSequence 和触发清理；后续调用只记录诊断，不得再次奖励、再次进入局终或覆盖失败原因。

首轮单人规则明确为：同一个服务器权威结算批次内若玩家气血已经归零，即使最后一个敌人也在该批次被击败，仍按失败处理，以符合“单人气血归零立即结束本局”的冻结规则。若胜利已经在更早的权威批次成功锁定，清理阶段取消的旧攻击不得再造成伤害。合作终局优先级继续保持未冻结，不从单人规则外推。

Timer、投射物、危险区和预警在创建时必须记录 `EncounterInstanceId` 与自己的稳定实例 ID；回调执行前同时校验战斗仍为 `Pending`、实例 ID 仍匹配且来源仍有效。清理按实例归属执行，不使用无边界的“销毁场上所有同类 Actor”。

### 8.1 战斗胜利

服务器确认遭遇目标完成后：

1. 通过 `TryFinalizeCombat` 原子设置胜利与战斗结算锁，拒绝新的技能和攻击请求；
2. 停止敌人 AI，取消所有前摇、延迟伤害、投射物和危险区域；
3. 保留短暂死亡/清场表现；
4. 显示“试炼已破”；
5. 只调用一次奖励发放；
6. 进入修炼或由未来章节节点决定的安全阶段。

`ActiveEnemyCount == 0` 可以继续作为清剿型遭遇条件之一，但不能成为所有未来遭遇的唯一完成规则。

### 8.2 单人死亡

当前冻结规则要求单人气血归零立即结束本局构筑并进入轮回。第一轮至少完成：

1. 玩家死亡后停止移动、攻击、施法和闪避请求；
2. 敌人停止追击已经死亡的目标；
3. 清理未结算的攻击、投射物、预警和表现 Actor；
4. 设置唯一失败原因，避免死亡与胜利同帧重复结算；
5. 进入局终界面，并允许从正式入口创建新的内存 Run、重新选择角色/门派并开始下一次轮回；
6. 为后续“删除活动局快照 → 提交界痕档案 → 新轮回”保留持久化接口。

第一轮不实现原地复活、章节复归、界痕档案写盘或活动局磁盘快照，但必须完成不依赖磁盘的“死亡 → 新 Run”轮回入口，不能只停在不可继续的临时失败画面。

工程实现补充（2026-08-30）：内存轮回现通过复制的 `MemoryRunSequence` 标识，重置前同步广播 `FW11MemoryRunResetContext`，新 Run 保留并继续推进全进程 `EncounterInstanceId / OutcomeSequence`，且明确重置玩家构筑、经济、属性状态、免疫和全部技能/闪避瞬态。该委托是持久化接线边界，不表示界痕档案或活动局快照已经写盘。

### 8.3 联机预留

在合作死亡规则冻结前：

- 不实现擅自设计的救援时长、共享复活次数或全队失败条件；
- 属性组件与玩家状态应能表达存活/不可战斗状态；
- 目标选择和遭遇完成逻辑不得假设永远只有一个玩家；
- 局终接口接受“失败玩家集合”和“仍存活玩家集合”，为后续规则留出边界。

## 9. 遭遇扩展顺序

第一轮完成单批清剿后，再按以下顺序扩展：

1. **波次清剿**：上一波结束后按定义延迟生成下一波；
2. **限时生存**：时间结束为完成条件，清怪只缓解压力；
3. **精英战**：普通机制组合、独立奖励和更强预警；
4. **章节小 Boss**：多阶段、固定机制检测，不只是生命倍率；
5. **最终 Boss**：检验整局构筑并承接剧情结局；
6. **地图章节路线**：战斗、事件、休整和仙坊成为独立节点，移除每战必进仙坊。

多人缩放采用“数量为主、生命温和增加、伤害轻微增加或不增加”的混合方案。当前 `1.0 + 0.45 × (人数 - 1)` 生命倍率只作为原型基线，必须配合敌人数、精英数和掉落节奏试玩，不能单独作为最终联机缩放。

## 11. 验证方案

### 11.1 自动化测试

在现有 `WorldWalker.W11` 组下增加以下测试方向，具体名称可按实现调整：

- `Combat.BasicAttackDefinition`：普攻不再依赖组件固定数值；
- `Combat.ServerRequestValidation`：施法者/槽位推导、频率、非有限输入、方向、目标点、资源、旧实例和死亡状态校验；
- `Combat.AbilityRejection`：失败原因、客户端请求序号和服务器冷却结束时间正确返回给请求玩家；
- `Combat.DamageBreakdown`：护体、护障、免疫、会心与实际伤害；
- `Combat.NonDamageEffects`：治疗、护障增加、回元与状态结果不通过生命差值猜测；
- `Combat.CooldownScaling`：普攻只受攻速、主动技能只受急速，除非定义显式覆盖；
- `Combat.StableMultiTargetOrder`：物理查询顺序变化时，最大目标数选择仍按稳定规则一致；
- `Combat.DodgeImmunity`：闪避窗口内免伤、窗口外正常受伤；
- `Combat.EnemyTelegraphLifecycle`：前摇、生效、后摇和取消；
- `Combat.EnemyTelegraphRecovery`：丢失瞬时 Cue 或中途加入时可由复制快照恢复预警；
- `Combat.ProjectileSingleHit`：弹体最多按定义命中并正确销毁；
- `Combat.CombatCueDeduplication`：相同结果序号不重复播放关键 Cue；
- `Combat.VictoryOnce`：清场只发放一次奖励；
- `Combat.DeathOnce`：死亡只进入一次局终；
- `Combat.MemoryRunLifecycle`：轮回序号、跨 Run Encounter/Outcome 单调性、重置前持久化委托和显式瞬态重置入口保持可反射契约；
- `Combat.NodeParticipantSets`：终局失败/存活 PlayerId 集合互斥、去重并稳定排序；
- `Combat.ChapterTransitionOwnership`：观察器不能隐式接管跳转，显式 owner 在有/无观察器时都保持唯一接管语义；
- `Combat.RecoveryPunishTelemetry`：只有后摇状态下造成的正生命伤害计入客观惩罚窗口指标；
- `Combat.ManualEvidenceSessionContract`：五类人工证据角色有效且各有独立可执行引导，任何无窗口、自动化、测试覆写、无音频或内部输入脚本都不能伪装成人工会话；
- `Combat.TerminalPrecedence`：单人胜利/死亡同一权威批次按冻结优先级得到唯一结果；
- `Combat.StaleEncounterCallbacks`：上一 Encounter 的 Timer、投射物和预警回调全部失效；
- `Combat.StageCleanup`：阶段切换后无残余伤害源；
- `Combat.ContentContracts`：三敌人和普通攻击定义字段完整、引用有效。
- `Combat.HudRuntimeNotificationContracts`：阶段/目标、护障、技能结果/冷却和闪避冷却保留可订阅的 RepNotify/委托入口。
- `Unit.DeterministicNameHash`：遭遇、敌人和随机用途名称使用稳定文本哈希，不依赖跨进程可变的 `FName` 索引。
- `Online.SteamEvidenceContracts`：只允许 Host/Client 证据角色和受限 Token；Null、App ID 480、非数字 App ID 与未冻结的迁移语义不能进入真实 Steam 发布证据。

### 11.2 无窗口冒烟

固定使用 `-W11RunSeed=424242 -W11AutoStart`，至少验证：

- 正确选择并加载 Hero、Sect、BasicAttack 和初始术法；

NullRHI 使用脚本化输入驱动规则闭环；单纯加载地图且没有可重复玩家输入不算战斗复现。NullRHI 只验证规则与状态机，不替代预警、HUD、音频和打击感的人工验收。

### 11.3 人工单人验收

使用至少三个不同门派完成固定 Seed 战斗：

1. 不攻击，分别观察三种敌人的攻击循环；
2. 只靠移动躲避瘴灵弹体；
3. 使用闪避穿过残剑魂攻击窗口；
4. 诱导石甲妖重砸后在后摇输出；
5. 验证普攻、范围术法、护障和治疗术法的反馈；
6. 分别触发普通伤害、会心、护障吸收、免疫和击败；
7. 主动战败一次，正常胜利一次；
8. 确认两种结果都没有残余攻击、重复奖励或输入泄漏；
9. 在 3840×2160 完成最终截图/录屏，并在三个兼容分辨率回归布局。

推荐从项目根目录使用 Final43 Cooked 总入口。它会在每次启动前验证 schema 4 整包全量清单和真实运行时目标，并把运行时用户数据和证据留在包外；随后直接等待真实游戏进程，按固定顺序逐局启动并等待真人完成。独立会话目录中的 schema 3 `session.json` 从第一局前开始记录进度、CookedGame、ProcessTarget 与 PackageHash，五局客观门禁全部通过后才生成签字包：

```powershell
.\Scripts\RunW11ManualAcceptance.ps1 `
  -Operator "<操作者姓名>" `
  -RuntimeMode Cooked `
  -PackageManifest "Saved/SteamAcceptance/Packages/W11Steam_Final43_Development/W11SteamPackageManifest.json"
```

`RuntimeMode Editor` 保留为开发调试入口，但正式真人收敛优先使用 Cooked；两者的会话来源会在最终封存证据中明确区分。

若流程中断，使用首次启动时显示的原会话目录继续；已有终局汇总的角色日志不会被覆盖，缺失角色会继续启动：

```powershell
.\Scripts\RunW11ManualAcceptance.ps1 `
  -Operator "<操作者姓名>" `
  -RuntimeMode Cooked `
  -PackageManifest "Saved/SteamAcceptance/Packages/W11Steam_Final43_Development/W11SteamPackageManifest.json" `
  -SessionDirectory "Saved/ManualAcceptance/Session_<时间>" `
  -SkipBuild `
  -Resume
```

总入口不会注入输入、自动开战、无窗口或无声音参数，必须由操作者在每个窗口里完成面板任务并正常退出。每局启动前会显示推荐门派、目标胜负和本角色操作说明，用于满足聚合器的三门派与胜负双路径覆盖；它们是采样建议，不会跳过角色/门派选择。每局退出后若缺少合法会话或终局汇总会立即停止，使用同一目录 `-Resume` 时会先保留无效日志再重试。可先用相同 RuntimeMode/PackageManifest 加 `-PlanOnly`，审阅五个角色、固定 Seed、运行时、PackageHash、覆盖建议、日志路径和输出包而不创建目录或启动游戏；`Scripts/verify_w11_manual_acceptance_launcher.ps1` 可重复验证 Editor/Cooked 两条入口契约。

也可以每次手工运行下列单角色入口；脚本默认固定 Seed `424242`、打开正常可视窗口，并在 `Saved/Logs` 生成带角色和时间戳的独立日志：

```powershell
.\Scripts\RunW11.ps1 -SkipBuild -ManualEvidenceRole Observe
.\Scripts\RunW11.ps1 -SkipBuild -ManualEvidenceRole Evasion
.\Scripts\RunW11.ps1 -SkipBuild -ManualEvidenceRole Dodge
.\Scripts\RunW11.ps1 -SkipBuild -ManualEvidenceRole Recovery
.\Scripts\RunW11.ps1 -SkipBuild -ManualEvidenceRole Feedback
```

进入游戏后，入口菜单右上角和战斗 HUD 会显示当前角色的允许/禁止操作、客观完成条件和退出提示；绿色表示会话环境可收录，红色表示本局无效并给出拒绝原因。进入战斗后，同一面板每 0.25 秒追加服务器权威的实时客观进度、已满足项目和违规状态。Evasion 只有在瘴气弹真正结束且未命中后才增加进度，不会把尚在飞行的弹体提前算作躲开。操作者仍应在验收记录中另写主观结论，不能只提交面板截图。

完成并退出每局后，以实际文件名执行：

```powershell
python Scripts/verify_w11_manual_acceptance_logs.py `
  --observe Saved/Logs/W11ManualObserve_<时间>.log `
  --evasion Saved/Logs/W11ManualEvasion_<时间>.log `
  --dodge Saved/Logs/W11ManualDodge_<时间>.log `
  --recovery Saved/Logs/W11ManualRecovery_<时间>.log `
  --extra Saved/Logs/W11ManualFeedback_<时间>.log
```

聚合器要求日志自身声明的角色与参数槽位一致、各文件唯一、会话和终局均为 Schema 3/Seed 424242/InputScript None，并要求会话标记同时证明有渲染、有音频、非自动启动、无测试覆写和 Standalone；随后覆盖三门派、胜负、观察、移动躲弹、闪避免疫、后摇惩罚及关键反馈。通过只代表客观事件齐全，仍需操作者另行确认预警是否看得清、闪避和镜头是否舒适、声音是否易区分及整体战斗是否好玩。

`--extra` 不是可省略的附加项：至少要提交一份由标准 `Feedback` 入口生成的日志，且关键反馈只能由该角色证明。客观门禁通过后，用相同五份参数生成正式记录：

```powershell
python Scripts/build_w11_manual_acceptance_packet.py `
  --observe Saved/Logs/W11ManualObserve_<时间>.log `
  --evasion Saved/Logs/W11ManualEvasion_<时间>.log `
  --dodge Saved/Logs/W11ManualDodge_<时间>.log `
  --recovery Saved/Logs/W11ManualRecovery_<时间>.log `
  --extra Saved/Logs/W11ManualFeedback_<时间>.log `
  --operator "<操作者姓名>" `
  --output Saved/ManualAcceptance/W11人工单人验收记录.md
```

生成的报告会把客观部分标为 `PASSED`、主观部分标为 `PENDING`；操作者必须填写设备、分辨率、耳机、每项备注、总体结论和签字。任何日志修改都会改变 SHA-256，届时必须重新门禁并重新生成。

同目录还会生成 `W11人工单人验收签字.json`。操作者必须逐项把九个 `result` 和四档 `visualEvidence` 从 `PENDING` 改为 `PASS` 或 `NEEDS_ADJUSTMENT`，填写非空备注、ISO 日期、输入设备、显示器、耳机/音频设备、性能观察、总体结论和签名。四张实际运行截图放在会话目录中，默认路径与真实像素必须分别为：

```text
VisualEvidence/W11_3840x2160.png
VisualEvidence/W11_2560x1440.png
VisualEvidence/W11_1920x1080.png
VisualEvidence/W11_1280x720.png
```

填写完毕后执行封存；封存器会重新核对五日志在客观报告中的 SHA-256、四张 PNG 的 IHDR 尺寸、九项结果与总体结论，再更新会话状态：

```powershell
python Scripts/finalize_w11_manual_acceptance_signoff.py `
  --session "Saved/ManualAcceptance/Session_<时间>/session.json"
```

只有输出 `W11_MANUAL_ACCEPTANCE_SIGNOFF_FINALIZED` 且 `Subjective=PASS / VisualEvidence=PASS` 时，才表示人工终态通过；`NEEDS_ADJUSTMENT` 是有效但不通过的真人结论，必须根据备注继续调参，不能改写成 PASS。

### 11.4 联机验收

第一轮至少使用 Listen Server 加一个客户端验证：

- 两端看见相同敌人状态、预警、命中目标和死亡结果；
- 客户端连续提交攻击不能绕过服务器间隔；
- 客户端闪避位移、免疫和最终位置与服务器一致；
- 一个玩家吸引仇恨时，另一玩家仍能正确命中；
- 玩家离开或死亡后敌人重新选择合法目标；
- 战斗奖励按当前规则发放一次，不因客户端表现事件重复。

在同一局域进程验收中增加至少一档网络延迟/抖动/丢包模拟，记录客户端实际可见预警提前量，并验证瞬时 Cue 丢失不影响持续攻击状态、冷却和终局恢复。另增加 Dedicated Server + 两客户端的最小无窗口冒烟，验证 AIController 仅在服务器存在时，客户端仍能取得攻击状态快照和合法终局。

真实 Steam 双机、邀请、NAT、重连和房主退出仍属于独立发布门禁；首轮中途加入只验攻击状态恢复能力，不承诺完整活动局重连流程。

真实 Steam 工具分为两个等级。`Integration` 使用 `UnrealEditor -game`，只用于提前检查 Steam OSS、Lobby Token 与同局 SessionId，输出不能作为发布证据：

```powershell
# 两台机器使用相同 AppId 与 Token，分别运行 Host / Client
.\Scripts\RunW11SteamAcceptance.ps1 `
  -Role Host -AppId "<项目 App ID>" -EvidenceToken "W11_<唯一批次>" -Mode Integration
.\Scripts\RunW11SteamAcceptance.ps1 `
  -Role Client -AppId "<项目 App ID>" -EvidenceToken "W11_<唯一批次>" -Mode Integration
```

正式 `Release` 必须传入已 Cook、已打包且两台机器内容版本一致的可执行文件；普通 Development Game 编译产物没有 Cooked 内容，不能替代打包程序。可先生成一个不额外注入验收项目 App ID、拒绝覆盖已有目录并带 SHA-256 清单的验收包；包内默认仍为可明确拒绝的 `Null / 480`，真实项目 App ID 仅由 runner 在进程级覆写：

```powershell
.\Scripts\BuildW11SteamAcceptancePackage.ps1 `
  -OutputDirectory "<全新输出目录>" -Configuration Development
```

为了让第二台机器不需要源码工程或 Unreal Engine 安装，可把包与验收工具封装为便携套件：

```powershell
.\Scripts\BuildW11SteamAcceptanceKit.ps1 `
  -PackageManifest "<包根目录>/W11SteamPackageManifest.json" `
  -OutputDirectory "<全新套件目录>"
```

当前已验证套件位于 `Saved/SteamAcceptance/Kits/W11Steam_Final43_Portable_v8`。复制到两台或最多四台机器后先运行 `.\Tools\TestW11SteamAcceptanceEnvironment.ps1 -AppId "<项目 App ID>" -Output ".\Saved\EnvironmentPreflight.json"`；只有 `Status=READY` 才表示本机前置条件齐全，仍不代表 Steam 联通通过。若得到 `ADMIN_REVIEW_REQUIRED / ACCESS_DENIED`，把 JSON 中的精确 runtime EXE 路径交给组织管理员。仍可手工运行 `python .\Tools\verify_w11_steam_acceptance_kit.py .\W11SteamAcceptanceKitManifest.json` 做显式完整性检查；runner 会在每次 PlanOnly/真实启动前和真实游戏退出后自动验证整套件。schema 3 套件会验证 5 个工具与 README 共 6 个制品的完整不可变集合、嵌套 schema 4 整包、真实运行时目标及双契约；套件内部运行证据只允许写入根级 `Saved/`。不要直接运行并继续分发已启动过的嵌套 Package 副本。Release runner 会生成 schema 2 收据；正式便携聚合必须传 `--kit-manifest .\W11SteamAcceptanceKitManifest.json`，不能降级。要求 Windows、Python 3、已登录且账号互不相同的 Steam 客户端、项目测试权限，以及组织策略允许最终 EXE 访问所需网络；不需要 `.uproject` 或 UnrealEditor。随后先用 `-Scenario BasicJoin` 在套件根目录分别运行：

```powershell
.\Tools\RunW11SteamAcceptance.ps1 `
  -Role Host -AppId "<项目 App ID>" -EvidenceToken "W11_<唯一批次>" `
  -Mode Release -PackageManifest ".\Package\W11SteamPackageManifest.json"
.\Tools\RunW11SteamAcceptance.ps1 `
  -Role Client -AppId "<项目 App ID>" -EvidenceToken "W11_<唯一批次>" `
  -Mode Release -PackageManifest ".\Package\W11SteamPackageManifest.json"
```

把两台机器生成的角色日志及其同名角色收据集中后执行正式 BasicJoin 聚合；默认不接受 EditorStandalone 日志：

```powershell
python .\Tools\verify_w11_steam_acceptance_logs.py `
  --host "<Host>/W11SteamBasicJoinHost.log" `
  --host-receipt "<Host>/W11SteamBasicJoinHostReceipt.json" `
  --client "<Client>/W11SteamBasicJoinClient.log" `
  --client-receipt "<Client>/W11SteamBasicJoinClientReceipt.json" `
  --scenario BasicJoin --expected-players 2 `
  --app-id "<项目 App ID>" `
  --token "W11_<唯一批次>" `
  --package-manifest ".\Package\W11SteamPackageManifest.json" `
  --kit-manifest ".\W11SteamAcceptanceKitManifest.json" `
  --output ".\Saved\Evidence\W11SteamBasicJoinEvidence.json"
```

只有 `W11_STEAM_ACCEPTANCE_BASIC_JOIN_PASSED` 证明 Cooked 双机以同 Scenario、Token、App ID、PackageHash 完成 Host/Find/Join，落在同一 SessionId，并由 Host 观察到目标人数；schema 5 聚合 JSON 还会封存套件清单 SHA-256、双时点验证契约、所有角色收据的 SHA-256 以及互不相同的 Steam64 `LocalUserId`。每台机器的单角色退出门禁和正式 Release 聚合都必须使用 `--package-manifest` 现场重验同一 schema 4 包；便携聚合还必须使用 `--kit-manifest` 重验同一 schema 3 套件并核对 schema 2 收据，不能用单独的 `--package-hash` 代替。复制改名的相同日志、混用不同套件或复用同一 Steam 账号也会失败。随后分别使用新的 Token 运行 `FriendInvite / HostExit / ClientDisconnect / PlayerSync`；四人同步聚合需要三次 `--client`、三次顺序对应的 `--client-receipt` 和 `--expected-players 4`。这些场景工具仍不证明 NAT 环境、重连、房主退出后的恢复策略或主机迁移；相应行为必须产生真实跨网络直接证据，且不得在规则冻结前自动实现迁移策略。

## 12. 数据记录与调参

每场测试至少记录：

- Run Seed、内容版本、规则版本、日志 schema、输入脚本 ID、角色、门派、普通攻击和主动技能；
- EncounterInstanceId、遭遇 ID、生成签名、敌人稳定 SpawnId、敌人组成、生成时间和清场时间；
- 玩家造成/承受伤害、会心次数、护障吸收、闪避次数与成功免伤次数；
- 每种敌人攻击次数、命中次数、取消次数；
- 真元消耗、回元、技能使用次数和失败原因；
- 胜利/失败、战斗总时长和剩余气血；
- 重复奖励、幽灵伤害、无预警伤害和卡死计数。

当前实现以服务器权威事件为输入：`W11_ABILITY_EFFECT` 保留逐效果的原始/减伤/护障/气血与状态事实，`W11_MANUAL_EVIDENCE_PROGRESS` 只在人工会话的角色进度发生变化时输出，`W11_ENEMY_PROJECTILE_EVADED` 在未命中弹体寿命结束时原子输出；终局再输出一条 `W11_COMBAT_SUMMARY`、逐玩家 `W11_COMBAT_SUMMARY_PLAYER`、逐敌人 `W11_COMBAT_SUMMARY_ENEMY`、逐技能与逐拒绝原因行。自动清怪等管理型伤害没有合法玩家来源，不计入玩家伤害或减伤，避免快速状态机测试污染平衡数据。

首轮体验目标：

- 三种敌人职责能够被玩家正确描述；
- 玩家首次遇见攻击时有实际反应窗口；
- 闪避重要但不是唯一生存手段；
- 近战和远程门派都存在输出窗口；
- 战斗不因敌人只是追脸叠在一起而退化为绕圈；
- 普通攻击、术法和敌人攻击的声音与 VFX 不互相淹没。

所有数值调整应写入定义资产或规则表，不在 Controller、角色名或敌人名分支中散落魔法数值。

## 13. 风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 规则和表现再次耦合 | Flipbook 播完才结算伤害 | 权威时点由服务器状态机和定义计时决定，动画只跟随 Cue |
| 网络瞬时事件丢失 | 客户端漏火花或声音 | 权威状态复制；瞬时 Cue 可丢失但不影响结果，关键阶段可由序号补偿 |
| AI 状态只存在服务器 Controller | 客户端无法恢复前摇或晚加入看到空状态 | 在 Enemy/战斗组件/预警 Actor 复制攻击实例、锁定几何和服务器时间戳 |
| 旧战斗回调污染新阶段 | Timer、弹体或危险区跨阶段命中 | 每个对象携带 Encounter/Attack 实例 ID，回调前校验，按实例清理 |
| 客户端伪造施法上下文 | 请求未装备技能、非法目标或 NaN 绕过校验 | RPC 所有者推导施法者，服务器按逻辑槽解析技能并验证有限数值、阶段、资源和目标 |
| 固定 Seed 被误当成完整复现 | Tick、物理查询顺序导致结果漂移 | 内容/规则版本、稳定 ID、稳定排序、隔离随机流和脚本化输入共同构成复现契约 |
| 预警过多遮挡画面 | 多人/多怪时地面全红 | 统一色义、透明度和同屏上限，按危险级别排序 |
| 打击停顿破坏联机 | 全局时间缩放导致状态漂移 | 仅做局部 Flipbook/材质/镜头表现 |
| 数据资产继续膨胀 | 每个敌人复制一套相同攻击 | 敌人引用共享敌方 Ability，参数差异通过定义或 Modifier 表达 |
| 四技能范围过早扩张 | HUD、输入、内容同时失控 | 第一轮只迁移普攻和现有初始术法，M5 再开放四槽 |
| 先做 Boss 导致返工 | Boss 重复使用临时直接扣血 | M1～M4 完成后再制作精英和 Boss |
| 当前 `F + Q/W/E/R + Space` 试玩键位被误当成不可改产品契约 | 后续手柄或重绑定困难 | 逻辑槽与物理输入分离，发布默认值与手柄映射持续标注为待定 |

## 14. 第一轮建议交付范围

第一轮开发只交付以下闭环：

```text
1 个数据驱动 BasicAttackAbility
+ 当前 6 个门派初始术法的统一执行兼容
+ EncounterInstanceId、唯一终局裁决与旧回调失效边界
+ 3 种拥有前摇/生效/后摇的敌人
+ 直线、圆形、投射物 3 类攻击原语
+ 可恢复的复制攻击状态快照
+ 通用技能执行/效果结果与命中 Cue
+ 命中火花、受击、数字和共享声音
+ 最小正式战斗 HUD
+ 单人胜利/死亡/清理与新内存 Run 入口闭环
+ 对应自动化、NullRHI 和人工验收记录
```

第一轮明确不包含：

- 五章完整路线；
- 五个章节小 Boss 和最终 Boss；
- 完整四主动技能内容池；
- 全部状态效果、召唤物、复杂连锁和武器进化；
- 合作倒地救援与房主迁移；
- 局外界痕档案、活动局快照和安全节点磁盘续玩；
